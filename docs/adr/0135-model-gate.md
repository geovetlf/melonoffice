# ADR-0135: model variants and the model gate (G-5)

- Status: Proposed
- Date: 2026-10-03
- Builds on: [ADR-0134](0134-evals.md) (evals), [ADR-0133](0133-prompt-versions.md) (prompt versions), [ADR-0100](0100-harness-provider-preference-and-task-budget.md) (routing)
- Decision: Geovet, 2026-10-03 18:52Z, "Autorización: continuar auditoría MelonOffice", block G-5 Optimization + Model Gate.
- Terraform: none. Firestore: none. No model, policy or route changes: every model stays DEV only.

## Context

G-4 measures the agents with a fixed set of cases. Two things were still missing:

- A way to compare variants (a prompt, a model, a route) on quality, cost, latency and reliability together.
- A rule that keeps a model from serving agents in staging or production before it has been measured.

The chain stays MelonOffice → Agent Engine → Model Router → Provider Adapter → Model.

## Decision

1. **Variants.** A run takes two new options:
   - `--model <provider/model>` holds the run to one model through the same router and policy. A model the policy leaves out is never called; its cases are `no_route`.
   - `--repeat <n>` (1 to 5) runs each case n times.

   A run records:
   - the dataset digest (a hash of its cases);
   - the pinned model;
   - the number of repetitions;
   - reliability: cases every candidate failed, and cases not run;
   - consistency: the share of cases whose repetitions all agreed.

   The comparison reports quality, cost, latency p50, reliability, consistency and the models used. A repeated case counts as passed only when every repetition passed. Runs over different cases are never accepted.

2. **Model reports.** `cli.js report <run.json>` turns a run held to one model into `docs/evals/reports/provider__model@version.json`. The report holds:
   - the model;
   - the prompt version;
   - the policy;
   - the dataset digest;
   - the date;
   - the pass rate;
   - the cost;
   - latency p50;
   - consistency.

   The report is committed. Its numbers are generated by the run, never typed by hand.

3. **The model gate.** A CI test (`packages/evals/src/gate.test.ts`) reads the Vertex AI, DeepSeek and NVIDIA catalogues. Every model whose definition and provider both allow `staging` or `prod` must have a committed report. That report must:
   - use the current agent task prompt version;
   - use the current dataset digest;
   - have every case answered by that model;
   - pass at least 90% of the cases (`MODEL_GATE_MIN_PASS_RATE`).

   Otherwise CI fails and names the model and the problem: `no_report`, `stale_prompt`, `stale_dataset`, `incomplete` or `below_threshold`.

4. **No exemptions.** Today every model is DEV only, so the gate passes with no reports. The first change that lets a model run outside DEV will need its report in the same PR. A new prompt version or a new set of cases makes every report stale, so the models outside DEV have to be measured again.

## Defaults chosen here, a person may change them

- The 90% threshold is a technical default, not a product decision. Raising or lowering it is a one-line change to a constant in `packages/evals/src/gate.ts`, reviewed like any other.
- Reports never expire by date. A date-based expiry would turn CI red with no change to the code. A report becomes stale only when the prompt, the cases or the model version changes.

## Not in this block

- A new provider package has to be added to the gate test's list. The test names the catalogues it reads.
- Choosing a dearer model that answers better stays a person's decision. The gate only refuses models that were not measured or that answer badly.

## Consequences

- A model cannot reach staging or production by a catalogue edit alone.
- Optimizing a prompt or a model is measured the same way each time and can be reverted on evidence.
